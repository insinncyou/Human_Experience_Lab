# Experience Critique

Experience Critique は、UI、プロダクト、サービス、空間、接客、広告、AIとの対話などを対象に、**人が実際に何を経験し、なぜそう解釈・行動したか**を観察から原則までたどる訓練フレームワークです。

これは「見た目の好き嫌い」や改善案の速さを競うレビューではありません。観察、因果推論、反証、抽象化を通じて、人間理解に根ざした設計判断をつくる練習です。詳細な進め方と評価基準は [`knowledge/09-experience-critique-framework.md`](../knowledge/09-experience-critique-framework.md) を参照してください。

## 使う場面

- ある画面・導線・空間・サービス接点で、体験の理由を深く理解したい
- 「良い／悪い」「使いやすい／使いにくい」を根拠ある説明へ変えたい
- 単発の事例から、条件付きで再利用できるExperience Principleをつくりたい
- JTBD、心理・行動、システム上の制約をつないで設計判断を考えたい

JTBDは「人がどの進歩を求めているか」を明らかにするときに使います。Experience Critiqueは、対象の体験全体を分解し、その進歩が支援・阻害される仕組みを批評するときに使います。両方が必要な場合は、ObservationとContextの後にJTBDを挟みます。

## 1セッションの流れ

1. **開始条件** — 題材、観察可能な証拠、問い、時間（15/30/60分）を確認する。対象が曖昧なら、まず一つの場面・利用者・時点に絞る。
2. **Observation** — 見た・聞いた・測った・引用した事実だけを記録する。評価語、原因、心理ラベルを混ぜない。
3. **Interpretation** — 事実が意味する可能性を複数置く。各解釈を事実と混同しない。
4. **Critical Questioning** — 「誰にとって、どの状況で、何と比べて、何が根拠か」「反対の説明は何か」を問う。
5. **Hypothesis / Causality** — 文脈→知覚・認知→行動→結果の因果鎖を、検証可能な仮説として書く。
6. **Psychology / Behavior / JTBD** — 必要な場合だけ、望む進歩、注意・理解・不確実性・動機・摩擦・フィードバック等の機序を仮説として接続する。
7. **Experience Judgment** — 何を最適化し、何を犠牲にするかを明らかにし、改善方向を比較する。解決策はこの段階より前に固定しない。
8. **Generalization / Application** — 条件、例外、リスクを含むExperience Principleへ抽象化し、別の場面での適用と反証条件を考える。
9. **Knowledge Capture** — テンプレートでResearch Noteを作成し、既存ノートとの重複・矛盾・接続候補を確認して保存する。

AIは研究コーチです。一度に一つの主要な問いを出し、ユーザーが二度詰まるまで答えを先に出しません。必要時だけ、観察の焦点、反証、比較仮説、短い例を提示します。三度詰まる、または直接の説明を求められた場合に限り、例示解答を出します。

## 事実を守るルール

| 区分 | 意味 | 書き方の例 |
|---|---|---|
| Observation | 直接確認できる事実 | 「確認ボタンの下に手数料が表示される」 |
| Reported | 当事者が述べた内容 | 「利用者は『不安だった』と述べた」 |
| Interpretation | 事実の意味づけ | 「重要情報に気づきにくい可能性がある」 |
| Hypothesis | 原因・機序の説明案 | 「確認順序が逆で、損失回避が強まるかもしれない」 |
| Known knowledge | 外部の知識・原則 | 出典と適用限界を併記する |

- 「高級」「直感的」「分かりやすい」「ユーザーは〜と思う」は、観察として書かない。何がそう見えた／そう推測した根拠を添える。
- 好みは無効ではないが、`Personal preference`として分離し、文脈への適合性と混同しない。
- 根拠のない断定、心理学用語による後付け説明、AIの即答、表層的なUI指摘だけで終えることを抑制する。
- 仮説は反証可能にし、少なくとも一つの代替説明と、次に必要な証拠を記録する。

## 完了条件

セッションは次の条件を満たしたときに終了します。

- 重要なObservationが解釈から分離されている
- 主要な仮説に根拠、確信度、代替説明、検証方法がある
- 心理・行動・JTBDを使った場合、それらが事実の代わりになっていない
- 設計判断にトレードオフと別案がある
- Principleに適用条件、避けるべきリスク、検証状態がある
- Research Noteに保存する価値、または保存しない理由が明示されている

## 知識への接続

保存前に、`Research_Notes/`をPrincipleの主要語、対象、体験結果で検索する。

- 同じ条件・同じ主張なら、既存ノートを更新候補としてリンクする
- 結論は近いが根拠や条件が異なるなら、補強・限定の関係を記録する
- 反対の結論なら、矛盾を消さず、条件差・証拠差・未解決点として残す
- 新しいPrincipleは「どの既存原則を広げる／狭める／反証するか」を明記する

1件の事例だけで原則を普遍化しません。原則は `Draft` または `Supported` とし、異なる文脈での再現・反証を待ちます。
